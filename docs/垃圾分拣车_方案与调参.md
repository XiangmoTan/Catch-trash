# 光电智能垃圾分拣车 —— 方案、原理与现场调参手册

> 对应代码：
> - OpenMV 端：`OpenMV/Car_For_Ball.py`（本次已重写）
> - 占空比标定：`OpenMV/duty_test.py`（新增）
> - STM32 端：`User/main.c`、`Hardware/vision_ctrl.c`
>
> 本文只解决两件事：**为什么现在不动**，以及**怎么一步步让它动起来并完成任务**。

---

## 0. 先给结论

1. **"数码管闪但车不走"不是通信问题。** 闪 = STM32 收到了校验正确的帧，通信链路是好的。
2. 真正原因是**视觉端根本没锁定目标**：
   - 旧代码只调用 `detect_bottle()`（红色），**绿色盒子完全没有检测分支**；
   - `detect_bottle()` 要求宽高比 **1.2 ~ 99**，而红色小球的宽高比约 **1.0**，被直接过滤掉；
   - 因此状态机永远停在 `SEARCH`，而 `SEARCH` 只发 `v=0, w=22`，即**原地旋转、不前进**；
   - 如果电池电压偏低，22% 占空比甚至可能低于电机启动死区，看起来就是"完全不动"。
3. 重写后的 `Car_For_Ball.py` 已经：
   - 正确识别红色小球（圆形）和绿色盒子（矩形）；
   - 用"红框 + 格子序号"的方法定位投放格；
   - 用状态机完成 搜索 → 对准 → 靠近 → 推 → 退回 → 再搜索；
   - 所有可能因场地而变的参数集中放在文件开头，带中文注释。

## 1. 系统是怎么工作的（原理）

### 1.1 整条链路

```
OpenMV H7 Plus
  摄像头拍图
    ↓
  LAB 颜色阈值分割（find_blobs）
    ↓
  形状/面积过滤（圆形？矩形？多大？）
    ↓
  像素误差 err = 目标x - 画面中心x
    ↓
  PID 算出角速度 w；面积误差算出线速度 v
    ↓
  UART3 发帧：0x2C 0x13 v w state chk 0x5B
    ↓
STM32 USART1 中断接收 → 校验 → s_v / s_w / s_state
    ↓
VisionCtrl_Task()：left = v - w, right = v + w
    ↓
TIM4 四路 PWM → 电机
```

### 1.2 为什么用 LAB 而不是 RGB

RGB 受光照强度影响很大：同一个红球，亮处和暗处的 R/G/B 完全不同。
LAB 把**亮度 L** 和**颜色 A/B** 分开了：

- **A 轴**：绿 ← → 红。红色物体 A 很大（正），绿色 A 很负。
- **B 轴**：蓝 ← → 黄。
- **L 轴**：亮度。

所以红色小球可以用"A 很大"稳定识别，绿色盒子用"A 很负"，再配合 L 范围排除阴影/高光。

### 1.3 面积当"距离尺"

同样的物体，离得越近，在画面里占的像素越多。近似关系：

```
面积 ∝ 1 / 距离²
```

所以不需要超声波/激光，直接用 `blob.pixels()`（或 `w*h`）就能判断远近：

- 面积小 → 还远 → 继续前进；
- 面积超过 `AREA_PUSH` → 已经贴到车头 → 切换到"推"。

⚠️ 面积阈值和**摄像头高度、俯仰角、分辨率**强相关，换车/换摄像头支架就必须重标。

### 1.4 差速轮运动学

STM32 里：

```c
left  = v - w;
right = v + w;
```

- `v > 0`：前进；
- `w > 0`：左轮慢、右轮快 → 左转；
- `w < 0`：右转；
- `v = 0, w > 0`：原地左转。

**符号必须和视觉误差一致**：目标在画面左边（cx 小）时，`err = 中心 - cx > 0`，应该 `w > 0` 左转，让目标回到画面中间。
如果实车转向相反，说明电机左右接反或 `w` 符号反了，见第 6 节。

### 1.5 串口帧与"闪 = 通信正常"

```
0x2C 0x13 v w state chk 0x5B
```

- `v`、`w`：`-100..100`，用 `& 0xFF` 转成字节；
- `state`：0 IDLE / 1 SEARCH / 2 APPROACH / 3 PUSH / 4 DONE / 5 BACK / 6 STOP；
- `chk = 0x2C ^ 0x13 ^ v ^ w ^ state`。

STM32 端 `Vision_Receive_Data()` **只有校验通过才置 `s_new_frame`**，
数码管闪烁正是由 `s_new_frame` 触发的，所以：

> **闪 = 至少每 400ms 收到一帧校验正确的数据。**

如果 400ms 没有新帧，`VisionCtrl_Task()` 会主动 `robot_speed(0,0,0,0)` 停车，这是安全保护。

### 1.6 状态机

```
IDLE
  ↓
SEARCH（原地左右扫描）
  ↓ 连续 3 帧检测到目标
APPROACH（先对准，再按面积靠近）
  ↓ 面积 >= AREA_PUSH 或目标贴到画面底部
PUSH（定速前进，同时用投放格做"车道保持"）
  ↓ 红框底边进入画面下部 72% 或超时
DONE（停 0.5s）
  ↓
BACK（后退 1.5s，离开投放区）
  ↓
SEARCH（继续找下一个）
```

几个关键设计：

- **连续 3 帧确认**（`DETECT_CONFIRM`）：防止一帧噪声触发误动作。
- **先转正再前进**（`ALIGN_ERR_PX`）：目标偏离中心超过 12 像素时只转不走，避免把球推歪。
- **底部触发**：物体离得太近会掉出画面下边缘，这时即使面积没到阈值也直接切 PUSH。
- **丢失保护**：APPROACH 中目标丢失超过 `LOST_MS` 就回 SEARCH；PUSH 中目标丢了仍然按原方向推（垃圾被车头挡住是正常的）。
- **走走停停搜索**：SEARCH 时“停 `STEP_PAUSE_MS` → 走 `STEP_GO_MS`”循环。
  停车期间图像不糊、能连续拍到多帧完成确认；瞬时占空比仍是 80%，
  不会掉到 55% 以下变成“通电但不转”。原理和调法见 Q10。

### 1.7 投放区怎么定位（重点）

场地示意图里，北侧有**两段红色线框**，每段里面有 4 个颜色的格子：

```
从左到右： 0 可回收(蓝)  1 厨余(绿)  2 有害(红)  3 其他(灰)
```

代码**不去识别每个格子的颜色**，而是：

1. 用 `find_dump_frame()` 找到红色线框的矩形 `(x, y, w, h)`；
2. 认为 4 个格子在红框内**等宽**排列；
3. 目标格中心：

```
bin_cx = x + w * MARGIN + (w * (1 - 2*MARGIN)) * (col + 0.5) / 4
```

其中 `col` 见 `BIN_COL`：

```python
BIN_COL = {
    KIND_BALL: 2,   # 红球 -> 有害垃圾(红格)
    KIND_BOX:  1,   # 绿盒 -> 厨余垃圾(绿格)
}
```

**为什么不用颜色直接找格子？**

- 绿色格子和绿色底板同色，很难分；
- 红色格子和红色线框同色，会粘成一团。

用"红框 landmark + 等分"最稳。只要现场的红框确实存在、4 格等宽，这个方法就成立。
如果现场红框不是等分，或者格子顺序不是图例顺序，只需要改 `BIN_COL` 和 `BIN_INNER_MARGIN`。

> 说明：本方案假设"红球 → 有害垃圾、绿盒 → 厨余垃圾"是按颜色对应。
> 如果裁判给的是别的分类规则，只改 `BIN_COL` 即可，其他代码不用动。

### 1.8 超声波避障（新增）

#### 为什么放在 STM32 端，而不是 OpenMV

避障是**安全兜底**：即使视觉程序卡住、串口断线（400ms 无帧 STM32 本来就会
停车），避障也必须在最后一刻生效。放在 STM32 的 20ms 控制循环里，可以直接
改写最终 PWM，不经过串口往返，也不占用 OpenMV 已经用掉的 UART。

#### 接线（默认）

| HC-SR04 | STM32 | 说明 |
|---|---|---|
| VCC | 5V | 模块要 5V，不要接 3.3V |
| GND | GND | — |
| TRIG | PB10 | STM32 输出 12us 高电平触发 |
| ECHO | PB11 | 模块输出，高电平宽度 = 声波往返时间 |

- PB10 / PB11 在 STM32F103 上属于 FT（5V 兼容）引脚，ECHO 可以直接接；
  板子若标注不支持 5V，用 1kΩ + 2kΩ 分压后再进 PB11。
- 换引脚只改 `Hardware/ultrasonic.c` 顶部的 `US_PORT`、`US_TRIG_PIN`、
  `US_ECHO_PIN` 三个宏，其他代码不用动。

#### 测距原理

```
TRIG 拉高 12us
   ↓
模块发 8 个 40kHz 脉冲，同时把 ECHO 拉高
   ↓
ECHO 高电平时间 t = 声波“去 + 回”的时间
   ↓
距离(mm) = t(us) × 343 / 2000
```

计时用 TIM1 配成 1MHz 自由计数（1 tick = 1us），读两次 `TIM1->CNT` 相减。
**不要**用 `Delay_us` 去量脉宽——它只能产生固定延时，量不了外部脉冲宽度。

每 60ms 测一次，最近 3 次有效值取中值；连续 3 次无回波就判定“没有障碍信息”，
避免传感器脱落/前方太空旷时一直拿着旧距离做避障，把车钉死在原地。

#### 避障动作

```
前方 < 150mm 且当前是 SEARCH 且 v > 0
   ↓
① 直退 350ms（v = -70）
   ↓
② 朝一侧弧线 700ms（v = 100, w = ±40）
   ↓
交还视觉指令
```

弧线用 `v=100, w=40`，内轮 = 100 − 40 = **60**，仍高于实测 55% 启动阈值，
不会出现“内轮被拖成刹车”的问题。

甩开方向只在“前方重新变空旷后又遇到新障碍”时才翻转；如果一直贴着同一个
障碍，会保持同方向继续甩，避免在墙角左一下右一下来回蹭。

#### 为什么默认只在 SEARCH 避障

APPROACH / PUSH 时车头前方**就是**要推的垃圾，不是障碍。如果这时候也避障，
车会在离垃圾 15cm 处被“劝退”，永远推不到。需要的话把
`AVOID_STATE_MASK` 从 `0x02` 改成 `0x06`（SEARCH + APPROACH），但要先把
`AVOID_START_MM` 降到 100 左右，确保不会在 PUSH 触发点之前拦车。

| 原来 | 现在 |

分两段自动扫描：

- **架空检查**：确认四个方向都能转、左右方向没接反；
- **地面扫描**：前进/后退/原地转（40~100）/弧线转（v=55），
  用来找"多少占空比电机才转得动"。

### 2.3 STM32 端

`PWM_DEADBAND` 保持 **20** 即可，**不要**改成实测的 55/80。

差速就被破坏了。真正该由 OpenMV 发多大的值，已经在
`V_CREEP` / `W_SEARCH` / `W_MIN_TURN` 里处理。

## 3. 现场标定流程（按顺序做，不要跳）

### Step 0：测电机最小占空比

**已测结果（当前这台车，2026-11）**：

- 前进最小 **55%**
- 后退最小 **60%**
- 原地左/右转：**60% 以内完全不动**

这个结果本身说明两件事：

1. 这台车的机械阻力很大（或电池电压偏低），前进都要 55%，属于偏高；
2. 原地转的启动阈值**明显高于 60%**，旧版 `duty_test.py` 只扫到 60，所以测不出来。

**工具**：车、场地、OpenMV 已连 STM32、电量接近比赛时的电池。

1. STM32 上电，按一下按键进入 **temp=2**（数码管闪烁）；
2. 先**把车架空**，运行 `OpenMV/duty_test.py`（`AIR_TEST = True`）：
   - `A3` 原地左转时，**左轮应向后、右轮应向前**；
   - `A4` 原地右转时方向相反；
   - 架空都不转 → 是接线/驱动板问题，先修硬件，别调参数；
3. 终端提示后把车放回地面，脚本继续测：
   - 前进 20~100、后退 20~100；
   - **原地转 40~100**（这次一直扫到 100）；
   - **弧线转：v=55，w=20~60**。

**根据结果三选一**：

| 现象 | 结论 | 怎么配 |
|---|---|---|
| 原地转在 70~90 能动 | 只是启动死区高 | `W_SEARCH` = 实测值 + 5，`W_MIN_TURN` = 实测值，`W_MAX` = 100 |
| 原地转 100 都不动，弧线能动 | 这台车无法原地转 | `TURN_ARC_V = 75`，`TURN_ARC_W = 25` |
| 架空时某个方向就不转 | 接线/驱动板问题 | 查电机线、驱动板通道，不要改参数 |

**为什么必须同时改 `W_MAX`**：

旧版 `W_MAX = 40`，而搜索和 PID 的输出都会在最后被它截断：

```python
if w > W_MAX:
    w = W_MAX
```

所以就算你测出"原地转要 80%"，程序也永远只发 40%，车还是不动。
现在 `W_MAX = 100`，测出多少就能发多少。

**前进/后退参数怎么填**：

- `V_CREEP`：实测 55 → 填 **60**（留 5 的余量）
- `V_BACK`：实测 60 → 填 **65**
- `V_PUSH`：填 **75**（推着东西负载更大）
- 电池电压下降后所有阈值都会升高，**在低电量下再测一次**，取更保守的值。

> 注意：车会真的跑起来，测试时前方留 2~3 米空地。

**如果最后只能用弧线模式**：把 `TURN_ARC_V` 设成 75、`TURN_ARC_W` 设成 25。
此时搜索和对准都是"边走边转"，车会画弧线而不是原地转，
这是两轮都向前滚、只是转速不同，阻力比原地转小得多，成功率高很多。
代价是搜索时车会往前走，`SEARCH_TIMEOUT_MS` 和场地边界要留意。

### Step 0.5：验证超声波（接线 / 量程）

1. 车放地面，进入 temp=2，OpenMV 正常发帧（数码管在闪）；
2. 在车头正前方 10cm、30cm、100cm 各放一块**硬纸板**
   （不要用红球测：球面会把声波散射掉，测不到是正常的）；
3. 期望行为：
   - **10cm**：SEARCH 时车应先后退 350ms，再朝一侧弧线 700ms；
   - **30cm / 100cm**：正常前进，不触发避障；
4. 如果 10cm 也不触发：
   - 先用万用表确认模块 VCC 是 **5V**（接 3.3V 大多数 HC-SR04 不工作）；
   - 确认 TRIG=PB10、ECHO=PB11 没接反、GND 共地；
   - 如果模块只有一个 SIG 引脚（单线型，如 AJ-SR04M / US-100），
     当前驱动不适用，需要单独告诉我型号改协议。

> 避障只改 STM32 的最终输出，OpenMV 的日志看不出区别；
> 判断是否生效只能看车的行为（后退 + 弧线）。

### Step 1：标定颜色阈值（最关键）

**工具**：OpenMV IDE → `工具(Tools)` → `机器视觉(Machine Vision)` → `阈值编辑器(Threshold Editor)`。

1. 把红球放在**比赛时它会出现的位置和高度**（不要拿在手里贴近镜头标）；
2. 调整 6 个滑块，让红球在二值图里**完整、边缘干净**，背景全黑；
3. 记录 6 个值，填到 `BALL_RED`：

```python
BALL_RED = [(L_min, L_max, A_min, A_max, B_min, B_max)]
```

4. 对绿色盒子重复一遍，填到 `BOX_GREEN`。

> **另一个"绿对绿"的坑**：投放区里的「厨余垃圾」格子本身也是绿色的。
> 代码已经处理：只要绿色候选落在检测到的红框**内部**，就当成投放格排除
> （`find_trash(img, frame)`）。如果现场绿格子不在红框内，或红框没被识别到，
> 这一步会失效，车可能朝投放区跑——先确认画面里有洋红色红框。

**绿色盒子的特殊问题**：场地底板也是绿色！

- 先看阈值编辑器里，盒子被选中的同时底板是否也被选中；
- 如果底板也被选中，说明两者颜色太接近，**颜色法基本失效**；
- 解决顺序：
  1. 收紧 `L` 范围，只保留盒子比底板亮/暗的那一段；
  2. 把盒子换成一个与底板色差更大的绿色；
  3. 在盒子周围贴一圈**黑色胶带**，用"黑色轮廓 + 内部绿色"的组合识别；
  4. 最后才考虑用 `find_rects()` 找矩形轮廓（对光影敏感，误检多）。

5. 对红色线框重复一遍，填到 `DUMP_RED`。红框是大块红色，通常比较好标。

**标定后立刻验证**：

- 把 `TARGET_KIND` 改成 `1`（只找球），运行程序，看画面里有没有黄框、终端有没有 `kind=1`；
- 再改成 `2`（只找盒），确认盒子能被框住、底板不会误触发；
- 最后改回 `0`。

### Step 2：标定面积阈值 `AREA_PUSH`

1. 在 `TARGET_KIND=1` 下运行，看终端打印的 `area=...`；
2. 把车慢慢推向球，记录车头离球 **10~15cm** 时的 `area`；
3. 把 `AREA_PUSH[KIND_BALL]` 设为记录值的 **80%~90%**；
4. 对盒子重复，设 `AREA_PUSH[KIND_BOX]`。

> 如果车还没到球就切 PUSH，说明阈值太小；如果车头顶到球了还没切，说明阈值太大或球已经掉出画面（这时靠 `BOTTOM_MARGIN` 兜底）。

### Step 3：标定对准 PID

参数：

```python
PID_X_KP, PID_X_KI, PID_X_KD = 0.45, 0.01, 0.10
ALIGN_ERR_PX = 12
```

观察现象与调整：

| 现象 | 原因 | 调整 |
|---|---|---|
| 车头左右摆个不停 | Kp 太大 / Kd 太小 | Kp 降到 0.30，Kd 加到 0.15 |
| 目标偏了但车转得很慢 | Kp 太小 | Kp 加到 0.60 |
| 转到位后还在慢慢漂 | Ki 太大 | Ki 设 0 |
| 到位很慢、总是差一点 | 死区太小 | `ALIGN_ERR_PX` 加到 15~20 |

调 PID 时把车**架空**（轮子离地），看轮子转向对不对、有没有抖动，再落地。

### Step 4：标定推动参数

```python
V_PUSH = 65
PUSH_MIN_MS = 800
PUSH_TIMEOUT_MS = 8000
FRAME_STOP_RATIO = 0.72
```

- `V_PUSH`：太小推不动，太大球会飞出去。建议比 `V_CREEP` 高 15~25。
- `FRAME_STOP_RATIO`：红框底边降到画面高度的多少时认为"到投放区了"。
  - 车停在投放区外面 → 调大（0.78~0.85）；
  - 车冲进投放区/撞框 → 调小（0.60~0.68）。
- `PUSH_TIMEOUT_MS`：兜底，防止红框没识别到时一直推。

### Step 5：标定投放格

1. 把车放在投放区正前方 1~2 米，`TARGET_KIND=0`；
2. 运行程序，看画面里洋红色矩形是否框住红框、PUSH 状态是否画出黄色竖线；
3. 黄色竖线应该落在**目标颜色格子**的中心：
   - 偏左/偏右 → 调 `BIN_INNER_MARGIN`（边框厚度）或 `BIN_COL`；
   - 如果现场 4 个格子不是等宽 → 需要把 `bin_center_x()` 改成查表：
     ```python
     # 例如现场实测 4 格中心占红框宽度的比例
     BIN_RATIO = {0: 0.12, 1: 0.37, 2: 0.62, 3: 0.87}
     ```
4. 如果现场红框不是红色（比如白线），改 `DUMP_RED` 阈值。

### Step 6：全流程联调

1. 电池充满；
2. 车放在起点框内，车头朝北（朝投放区）；
3. STM32 进入 temp=2；
4. 先只放**一个红球**，观察：搜索 → 对准 → 推 → 停 → 后退；
5. 成功后再放**一个绿盒**；
6. 最后放两个，观察"推完一个能否退回来找下一个"。

## 5. 常见问题排查

### Q0：升级 OpenMV 固件后报 `TypeError: object 'int' isn't a tuple or list`

OpenMV 5.x 改了绘图 API：坐标必须写成元组。

```python
# 旧固件
img.draw_string(2, 2, "SEARCH")
# OpenMV 5.x
img.draw_string((2, 2), "SEARCH")
```

代码里已经用 `try/except TypeError` 同时兼容两种写法。
`draw_rectangle` / `draw_line` / `draw_cross` 本来就是元组写法，不受影响。

### Q0.5：报 `TypeError: 'tuple' object isn't callable`

OpenMV 5.x 把 blob 的 `rect/cx/cy/pixels/roundness/solidity`
从**方法**改成了**属性**：

```python
b.rect()      # 旧固件
b.rect        # OpenMV 5.x
```

代码里统一走 `_rect()` / `_blob_int()` / `_roundness()` / `_solidity()`
四个兼容函数，两种固件都能跑。换固件后如果还报类似的
“xxx object isn't callable”，把出错行发出来，按同样方式包一层即可。

### Q1：数码管闪，但车还是不动

按顺序查：

1. **看 OpenMV IDE 的终端**：是不是一直 `no target`？
   - 是 → 阈值/形状过滤问题，回 Step 1；
   - 不是 → 看 `v/w` 是不是 0。
2. `v=0, w=75` 且车不转 → 见 Q1.5：先架空确认方向，再提高 `W_SEARCH` 或改弧线。
3. `v>0` 但车不动 → 电池电压/电机驱动/轮子打滑，先用 `duty_test.py` 在 100% 下确认能走。
4. 车能走但**不往前走，只原地转** → 正常，SEARCH 状态就是在原地找目标。

### Q1.5：前进/后退正常，左右完全不转（当前遇到的情况）

按顺序判断，不要先怀疑颜色阈值：

1. **架空测**（`duty_test.py` 的 A3/A4）：
   - 轮子不转或方向不对 → 接线/驱动板通道问题，先修硬件；
   - 轮子能一正一反地转 → 说明电机和方向控制都没问题，继续第 2 步。
2. **地面原地转 40~100**：
   - 70~90 能动 → 只是启动死区高：`W_SEARCH` = 实测值 + 5，
     `W_MIN_TURN` = 实测值，`W_MAX` = 100；
   - 100 都不动 → 这台车靠原地转是转不动的，用第 3 步。
3. **改用弧线模式**：`TURN_ARC_V = 75`、`TURN_ARC_W = 25`。
   两轮都向前，只是转速不同，阻力比原地转小得多。

同时检查：

- **电池电压**：原地转最吃扭矩，电压一低最先转不动；
- **`W_MAX` 是不是还是旧的 40**：它会把搜索和 PID 的输出全部砍到 40；
- 轮子是否打滑、地面是否太涩、车是否太重。

> 实测参考：当前这台车前进 55%、后退 60% 才动，属于阻力偏大，
> 原地转的阈值大概率在 70% 以上；先按第 2、3 步试，不要死磕原地转。

### Q1.6：日志里能看到球（kind=1），但车完全不动

先看日志里的 `v` 和 `w`：

- 弧线模式：`内轮 = v - w`，**必须 ≥ 实测前进最小值（55）**。
  例：`v=55, w=20` → 内轮 35，低于启动阈值，但驱动板还在给它通电，
  等于**拖着刹车走**，外轮 75 也带不动，整车看起来完全静止。
  改成 `v=80, w=20` → 内轮 60、外轮 100，两个轮子都真正在转。
- `v` 不要刚好等于实测阈值（55），至少留 10~15 的余量，否则电池稍降就不动。
- 再确认：数码管在闪（temp=2）、电池有电、单独跑 `duty_test.py` 车能走。

### Q1.7：APPROACH 和 SEARCH 反复来回跳

这是旧代码的计时 bug：它用"进入 APPROACH 多久"判断目标丢失，
只要在 APPROACH 里待超过 400ms，中间**漏检一帧**就立刻退回 SEARCH。
现在已经改成用"最后一次看到目标的时刻"计时，并且短暂丢失时
会朝目标最后消失的方向继续找，不再急停/盲翻转。

如果还跳，说明检测本身不稳定：把 `BALL_MIN_PX` 调小（40），
检查 `BALL_RED` 阈值是否覆盖了球在各种距离/光照下的颜色。

### Q1.8：远处的球识别不到，要不要主动靠近？

对，必须主动靠近。原因：

- QQVGA 下远处的球只有几个像素，低于 `BALL_MIN_PX` 就被当噪声；
- 远处的球在画面**上方**，旧的 `BALL_TOP_GUARD=0.30` 会把它全部误杀。

现在已改成 `BALL_TOP_GUARD=0.0`、`BALL_MIN_PX=40`，检测距离会明显变远。
另外 `TURN_ARC_V=80 > 0` 时，搜索状态是"边走边转"，
车会一边扫一边前进，自然靠近目标。如果还想更远，可以把分辨率
从 QQVGA 改成 QVGA（320×240，像素数 4 倍），代价是帧率下降。

### Q2：车原地转，但目标明明在正前方

- 阈值没框住目标（最常见）；
- `TARGET_KIND` 设错了；
- 目标太远，`AREA_MIN` 或 `BALL_MIN_PX` 把它过滤了；
- 宽高比/圆度过滤太严。

**调试技巧**：在 OpenMV IDE 里看**实时画面**，而不是只看终端。代码会把检出的目标画成黄色矩形，没框住就一目了然。

### Q3：车朝目标的反方向转

- 电机左右接反，或 `w` 符号反了。
- 验证：在 `duty_test.py` 里 `w=+20` 应该是**左转**。
- 修正二选一：
  1. 对调左右电机线；
  2. 把 `vision_ctrl.c` 里 `set_wheels(v - w, v + w)` 改成 `set_wheels(v + w, v - w)`。
- 注意：改完要重新验证前进方向。

### Q4：球被推歪/滚走

- 球是圆的，容错低：`ALIGN_ERR_PX` 调小（8~10），`PID_X_KP` 适当加大；
- `V_PUSH` 降低一点，避免撞飞；
- 检查车头是否有足够的"推板"面积。

### Q5：绿盒识别不到

- 底板和盒子都是绿色 → 这是最可能的原因，见 Step 1 的解决顺序；
- 盒子太矮，`BOX_MAX_AR` 太大/太小；
- 盒子被其他垃圾挡住。

### Q6：到投放区不停/不停在正确位置

- `FRAME_STOP_RATIO` 没调好；
- 红框没被识别到（被遮挡/阈值不对）→ 看画面洋红色框；
- `PUSH_TIMEOUT_MS` 兜底生效。

### Q7：推完一个回不来

- 没有编码器/陀螺仪，后退是**按时间估算**的；
- 加大 `BACK_MS`；
- 如果地面打滑，`V_BACK` 调大但时间相应减小；
- **如果车退回来后又被同一个垃圾吸引并重复推**：说明上次没把垃圾推进红框内。
  加大 `PUSH_MIN_MS`，或把 `FRAME_STOP_RATIO` 调大一点（0.76~0.80）。
  垃圾一旦进了红框，`find_trash()` 的红框排除逻辑会让它"消失"，车就会去找下一个；
- 实在不行，改成"推完原地 180° 掉头再回来"（需要加计时转向状态），但更不精确。

### Q8：电池电压下降后行为变化

- 电机转速下降 → 同样时间走得近 → `PUSH_TIMEOUT_MS`/`BACK_MS` 需要更大；
- 最小启动占空比上升 → 低速档可能转不动；
- **比赛前换满电电池，并在低电量下复测一次**。

### Q9：加了超声波后车不走 / 一直后退打转

先分清是“真检测到障碍”还是“传感器误报”：

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 前方空旷，车却反复后退 + 弧线 | ECHO 被固定拉高/拉低，读数卡在几十 mm | 查 GND 是否共地、ECHO 是否误接到 5V；空闲时 ECHO 应为 0V |
| 10cm 放硬纸板也不触发 | 模块供电不足 / TRIG 没接对 / 是单线模块 | 确认 VCC=5V、TRIG=PB10；单线模块要改驱动 |
| 车贴着垃圾不推 | 避障在 APPROACH 也生效了 | 确认 `AVOID_STATE_MASK = 0x02` |
| 退一点又前进，来回抖 | 触发距离太接近实际停车距离 | `AVOID_START_MM` 加到 200，或 `AVOID_BACK_MS` 加到 500 |
| 想临时关掉避障 | — | `AVOID_ENABLE` 改 0 重新编译 |

注意：超声波测的是**最近的大平面**。球面、斜面、软布会散射/吸收，测不到是
正常的；避障主要防的是墙、桌腿、投放框这类硬平面。这也是为什么默认不在
APPROACH / PUSH 避障——那里的目标是垃圾，不是墙。

### Q10：车跑得太快，来不及识别 / 一晃就过去了

**先想清楚为什么不能简单地“把速度调小”**：实测这台车低于 55% 根本不转，
所以 `TURN_ARC_V` 不能无限往下设；而且内轮 = `TURN_ARC_V − TURN_ARC_W`
还必须 ≥ 55，能慢的空间很小。

正确做法是**走走停停**（`SEARCH_STEP = True`）：

```
停 STEP_PAUSE_MS（v=0, w=0，轮子断电自由滑行）
   ↓
走 STEP_GO_MS（正常弧线，瞬时占空比仍是 80%，保证能起步）
   ↓
循环
```

好处：

1. 停车时图像不糊，远处只有几十像素的小球才能稳定分割出来；
2. 停 300ms 能拍到约 9 帧（30fps），足够完成 `DETECT_CONFIRM = 3` 的连续确认；
3. 瞬时占空比没变，不会掉到 55% 以下变成“通电但不转”。

调法：

| 现象 | 调整 |
|---|---|
| 还是冲过头 | `STEP_GO_MS` 300→200，或 `STEP_PAUSE_MS` 300→400 |
| 半天走不到垃圾 | `STEP_GO_MS` 300→500 |
| 接近目标时还是太快 | `V_APPROACH_MAX` 65→60（别低于 55） |
| 停的时候车滑太远 | 地面太滑；把 `STEP_PAUSE_MS` 加长，或临时在 STOP 时反向点刹 |

如果确认是**运动模糊**（画面里目标拖影），还可以在 OpenMV 开头加：

```python
sensor.set_auto_exposure(False, exposure_us=8000)   # 缩短曝光
sensor.set_auto_gain(False)
```

但室内光线暗时会导致画面过暗、LAB 阈值失效，**先试试走走停停，通常就够了**。

## 6. 还需要你确认的几件事

这些直接影响参数，建议先确认再调：

1. **红色小球、绿色盒子的实际尺寸**（直径/长宽高）——决定 `AREA_PUSH` 和形状过滤。
2. **绿色盒子和场地底板的色差**——如果几乎同色，必须换盒子或加标记。
3. **投放区 4 个格子的实际顺序和是否等宽**——决定 `BIN_COL` 和 `bin_center_x()`。
4. **红球/绿盒分别应该进哪一类**——目前按颜色假设：红球→有害(红格)，绿盒→厨余(绿格)。
5. **一辆车只跑一次还是可以多次出发**——影响"退回再找下一个"的策略。
6. **比赛时电池的电压范围**——决定 `V_CREEP`/`W_SEARCH` 的保守程度。
7. **超声波模块的型号和实际接线**——当前按 HC-SR04（TRIG=PB10、ECHO=PB11）
   编写。如果你的模块是单线型（AJ-SR04M/US-100）或接在别的引脚上，
   告诉我型号/引脚，我改驱动。
